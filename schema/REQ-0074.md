## 1. Normative Statement

The interconnect engine SHALL formalize SysML v2 connection definitions (`connection def`, `ConnectionDefinition`) and connection usages (`connection`, `connect`, `Connector`) as relational association structures binding two or more port endpoints. `ConnectionDefinition` SHALL specialize KerML `AssociationStructure` and `Structure`.

The lowering engine MUST enforce endpoint type compatibility and directional flow legality across all connection usages:
1. **Endpoint Type Conformance**: For a binary connection $``C = (p_1, p_2)``$ between port endpoints $``p_1``$ and $``p_2``$, the source port type MUST conform to the conjugate of the target port type: $``\tau(p_1) \le {\sim}\tau(p_2)``$. Type mismatches across connected endpoints SHALL emit diagnostic `E0200`.
2. **Directional Flow Legality**: Connected port directions MUST be compatible: an `Out` port SHALL connect exclusively to an `In` or `InOut` port ($``\text{dir}(p_1) = \text{Out} \implies \text{dir}(p_2) \in \{ \text{In}, \text{InOut} \}``$). Conflicting directions (e.g., `Out` to `Out` without mediation) SHALL emit diagnostic `E0200`.
3. **Topological Scope Visibility**: Both connection endpoints $``p_1``$ and $``p_2``$ MUST resolve to accessible port usages within the common enclosing component or across immediate peer component boundaries. Out-of-scope or dangling endpoint paths SHALL emit diagnostic `E0200`.

## 2. Formal Invariant

Let $``\mathcal{D}_{\text{conn}}``$ denote connection definitions and $``\mathcal{E}_{\text{conn}}``$ denote lowered connection instances:

```math
\begin{aligned}
\text{ConnectionDefinition} &\le \text{AssociationStructure} \le \text{Structure} \\
C = (p_1, p_2) \in \mathcal{E}_{\text{conn}} &\implies \tau(p_1) \le {\sim}\tau(p_2)
\end{aligned}
```

Directional flow legality and topological endpoint scoping invariant:

```math
\begin{aligned}
\text{dir}(p_1) = \text{Out} &\implies \text{dir}(p_2) \in \{ \text{In}, \text{InOut} \} \\
\text{dir}(p_1) = \text{In} &\implies \text{dir}(p_2) \in \{ \text{Out}, \text{InOut} \} \\
\text{LCA}(p_1, p_2) &\in \text{Ancestors}(C) \cup \{ \text{Owner}(C) \}
\end{aligned}
```

Multi-point connector and RFC 4122 UUIDv5 invariants:

```math
\begin{aligned}
|\text{Endpoints}(C)| &\ge 2 \\
\forall n \in \mathcal{D}_{\text{conn}} \cup \mathcal{E}_{\text{conn}}, \quad \Delta_n &= \text{UUIDv5}(\text{NS}_{\text{DEAP}}, \text{FQN}(n))
\end{aligned}
```

## 3. Computational Complexity & Algorithmic Bounds

The connection definition lowering, endpoint resolution, and compatibility checking passes execute strictly within Complexity Class $\mathbf{P}$.

For an input model with $E$ connection usages and $V$ port endpoints:
1. Endpoint resolution in hierarchical symbol tables executes in $O(1)$ amortized time per endpoint, totaling $O(E)$ time.
2. Endpoint type conformance checking against the conjugate type lattice evaluates in $O(1)$ time per connection, grounding the polynomial fragment of NP-3.
3. Directional flow compatibility checks execute in strictly $O(1)$ scalar comparisons per connector.
4. Topological scope visibility validation verifies lowest common ancestor containment in $O(D)$ time where tree depth $D \le 16$ (REQ-0070), bounded by $O(1)$ constant time.

Total sequential verification complexity is $O(E + V)$. Parallel package lowering scales as $``O((E + V) / N_{\text{max\_workers}} + \log N_{\text{max\_workers}})``$.

## 4. Verification & Conformance Criteria (IEEE 29148 Acceptance Criteria)

### AC-01: Canonical Connection Lowering and Conjugate Compatibility
- **Given:** A connection `connect Part_Alpha.Port_Out to Part_Beta.Port_In` where `Port_Out : PortDef_Alpha` and `Port_In : ~PortDef_Alpha`.
- **When:** The compiler executes connection lowering and interface compatibility verification.
- **Then:** The connector is lowered into arena storage with bound endpoints and zero diagnostic emissions.
- **Diagnostic:** `E0200` emitted if conjugate compatibility check fails.

### AC-02: Conflicting Directional Flow Rejection
- **Given:** A connection binding two output ports directly together (`connect Part_Alpha.Port_Out1 to Part_Beta.Port_Out2`).
- **When:** Semantic directionality validation analyzes endpoint interaction modes.
- **Then:** The compiler rejects the conflicting output connection at compile time and emits diagnostic error code `E0200`.
- **Diagnostic:** `E0200` emitted for conflicting port flow directions.

### AC-03: Incompatible Port Type Rejection
- **Given:** A connection binding incompatible port definitions `PortDef_Alpha` and `PortDef_Beta` where $``\text{PortDef\_Alpha} \not\le {\sim}\text{PortDef\_Beta}``$.
- **When:** Semantic type checking validates endpoint conjugate conformance.
- **Then:** The compiler rejects the connector declaration and emits diagnostic error code `E0200`.
- **Diagnostic:** `E0200` emitted for port type incompatibility.

### AC-04: Out-of-Scope Dangling Endpoint Detection
- **Given:** A connection referencing an inaccessible or non-existent port path `Part_Alpha.NonExistentPort`.
- **When:** Endpoint namespace resolution is evaluated.
- **Then:** The compiler halts connection lowering for the dangling endpoint and emits diagnostic error code `E0200`.
- **Diagnostic:** `E0200` emitted for unresolved or out-of-scope connection endpoint.
