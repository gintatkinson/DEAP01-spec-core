## 2. Logic Chain

From the observations above, we establish the following deductive sequence:

1. **Parameter Expansion Placement (Observation 1.3):**
   - The downstream customer onboarding command must embed the concrete detected remote URL (`$DOMAIN_REMOTE_URL`), not a literal bash variable string (`"$DOMAIN_REMOTE_URL"`) and not an unquoted angle-bracket placeholder (`<domain-repo-remote-url>`).
   - Because line 643 starts a quoted heredoc (`cat << 'EOF'`), any content placed after line 643 cannot expand bash variables.
   - Therefore, the Customer Project Onboarding section must be generated before line 643, within the expanding heredoc block (`cat << EOF`).

2. **Remote URL Resolution Priority (Observations 1.1 & 1.3):**
   - In Tier 1 propagation (from `DEAP01-spec-core` into a domain template like `DEAP-uas-infrastructure-safety`), `$TARGET_DIR` is the domain repository. Its git remote represents the domain repository remote.
   - However, if the domain repository's remote still points to `DEAP01-spec-core` (or contains `DEAP01-spec-core`), using it would violate R2 by pointing customer onboarding back to the compiler repository.
   - In Tier 2 propagation (when running `install_pipeline.sh` from `./.tmp-pipeline` into a customer project), `$INSTALLER_ROOT` is the domain template, whereas `$TARGET_DIR` is the customer application workspace.
   - Therefore, resolution must follow a strict 4-tier hierarchy:
     - **Tier A:** `$REMOTE_URL` from `$TARGET_DIR` if non-empty and does not contain `DEAP01-spec-core`.
     - **Tier B:** Normalized HTTPS URL `${DETECTED_SERVER_URL}/${DETECTED_NAMESPACE}/${DETECTED_PROJECT}.git` if detected project is not `DEAP01-spec-core`.
     - **Tier C:** If installer is running from a downstream distribution template (`[ ! -e "$INSTALLER_ROOT/.pipeline/upstream" ]`), query `$INSTALLER_ROOT` git remote `origin` (if not containing `DEAP01-spec-core`).
     - **Tier D:** Concrete fallback constructed from detected server/provider, detected namespace or group, and domain project name (e.g. `https://github.com/${GITHUB_ORG:-your-org}/${CLEAN_PROJECT_NAME}.git` or `${GITLAB_URL:-https://gitlab.com}/${GITLAB_GROUP:-your-group}/${CLEAN_PROJECT_NAME}.git`).
   - This ensures `$DOMAIN_REMOTE_URL` is never empty, never contains `DEAP01-spec-core`, and never contains unquoted angle brackets or placeholders.

3. **Section Architecture and Numbering Preservation (Observation 1.3):**
   - If an onboarding section is inserted as a new top-level `## 3. Installation & Customer Onboarding` and `## 3. Mandatory Agent Initialization Sequence` is renumbered to `## 4`, then Section 4 (`Multi-Pipeline Operator Prompt Catalog`) would need to become Section 5.
   - Changing Section 4 to Section 5 would create a major discrepancy with lines 648–1088, where all subsections are numbered `### 4.1`, `### 4.2`, `#### 4.2.1`, `### 4.3`, `### 4.4`, `### 4.5`, and `#### 4.5.3`. Renumbering all of those subsections touches over 400 lines of complex markdown and prompt code blocks.
   - **Recommended Solution:** Structure Section 3 as:
     - `## 3. Customer Project Onboarding & Agent Initialization Sequence`
       - `### 3.1 Turnkey Customer Project Onboarding` (contains the single-command onboarding instruction and in-place update command)
       - `### 3.2 Mandatory Agent Initialization Sequence` (contains existing steps 0 through 5)
   - This keeps Section 1, Section 2, Section 3, Section 4 (`4.1`–`4.5.3`), and Section 5 (`Verification & Quality Gates`) perfectly aligned and unbroken without requiring invasive changes to the 400-line prompt catalog.

4. **Formatting of Onboarding Command & Code Blocks (Observations 1.1, 1.3):**
   - The customer onboarding command must be:
     ```bash
     # Onboard customer application workspace
     git clone ${DOMAIN_REMOTE_URL} ./.tmp-pipeline && bash ./.tmp-pipeline/scripts/install_pipeline.sh . && rm -rf ./.tmp-pipeline
     ```
   - In-place update command:
     ```bash
     # Update existing customer application workspace
     bash scripts/install_pipeline.sh .
     ```
   - Rules strictly honored:
     - Shell comments contain **zero parentheses** (`# Onboard customer application workspace`).
     - Shell code block contains **zero unquoted angle-bracket placeholders** (`${DOMAIN_REMOTE_URL}` expands to the concrete URL).
     - Inside `cat << EOF`, backticks must be escaped as `\`\`\`bash` and `\`\`\`` so that bash does not attempt subshell execution.

5. **Update Trigger Condition (Observation 1.2):**
   - Line 478 should also check `! grep -qE "Customer Project Onboarding|\.tmp-pipeline" "$TARGET_DIR/README.md"` so that existing downstream repositories updated via `install_pipeline.sh` automatically receive the new onboarding section.

## 3. Caveats

1. **Target Directory Git State:**
   - If `$TARGET_DIR` is initialized without any remote and no project metadata exists, Tier D fallback will construct a URL using `your-org` / `your-group`. This is a valid, well-formed URL without angle brackets, but requires the user to substitute their organization if they have not yet configured git remotes.
2. **SSH vs. HTTPS Remotes:**
   - If a domain maintainer configured an SSH remote (`git@github.com:...`), Tier B normalization constructs a universal HTTPS URL (`https://github.com/...`) which is friendlier for downstream customer onboarding (does not require customer machines to have specific SSH keys pre-registered for the domain repository).
3. **Upstream Compiler Refusal Invariant:**
   - `scripts/install_pipeline.sh` refuses to run in-place on `DEAP01-spec-core` due to lines 163–169 (`REFUSING: target is the pipeline repository itself`). Therefore, downstream README generation never overwrites `DEAP01-spec-core/README.md`.
